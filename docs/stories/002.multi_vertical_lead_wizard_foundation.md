# Story 2.1: Multi-Vertical Lead Wizard Foundation

## Status
- **Status**: In Progress
- **Executor**: @dev
- **Quality Gate**: @architect
- **Quality Gate Tools**: [RSpec, Jest/Vitest, TypeScript, ESLint]

---

## Story
**As a** usuário interessado em orçamento por uma vertical específica,  
**I want** que o wizard resolva a categoria correta e persista respostas dinâmicas sem quebrar o fluxo atual,  
**so that** eu receba um formulário aderente ao serviço desejado e o sistema continue compatível com o funil legado.

---

## Contexto do Problema
O projeto já possui a infraestrutura base para um wizard dinâmico por categoria:

- tabela `category_lead_wizards`
- endpoint `GET /api/v1/lead_wizards/resolve`
- serviço `LeadWizard::Creator`
- armazenamento de campos variáveis em `leads.wizard_answers`

Mas o código atual ainda está parcialmente acoplado ao fluxo solar legado:

- o `Resolver` ignora na prática a disponibilidade por empresa
- o `Lead` exige um core fixo de campos do wizard solar para qualquer lead não-draft
- o frontend dinâmico separa muitos campos em `wizard_answers`, enquanto o backend ainda depende de colunas reais do `Lead`
- o fallback existe, mas ainda não diferencia claramente indisponibilidade de empresa vs. ausência de wizard

Esta story cobre a fundação do fluxo multi-vertical usando a **Estratégia A de compatibilidade forte**:

- manter o core obrigatório atual do `Lead`
- mapear explicitamente o mínimo necessário para as colunas reais
- manter `wizard_answers` como source of truth dos campos variáveis
- reutilizar os endpoints e serviços existentes

## Estado Atual e Limitações
- `fields[].key` já é o contrato implícito do schema e não pode ser trocado por `name`.
- `preferred_company_id` já trafega, mas ainda não produz filtro real no `LeadWizard::Resolver`.
- o `LeadWizard::Creator` persiste `wizard_answers`, porém ainda resolve template sem considerar a empresa.
- o frontend dinâmico já usa `/lead_wizards/resolve`, mas seu `buildPayload` ainda não cobre o core obrigatório do `Lead` de forma confiável para jornadas multi-vertical.

## Escopo da Story
- Formalizar o contrato inicial de `category_lead_wizards.schema` com base em `fields[].key`.
- Estender o `LeadWizard::Resolver` para considerar `preferred_company_id` como filtro de disponibilidade via `categories_companies`.
- Preservar `GET /api/v1/lead_wizards/resolve` como contrato único de leitura.
- Garantir que `LeadWizard::Creator` resolva template e validação usando o mesmo contexto de categoria + empresa.
- Manter `leads.wizard_answers` como source of truth dos campos variáveis.
- Garantir mapeamento explícito entre payload do frontend, colunas reais do `Lead` e `wizard_answers`.
- Alinhar o frontend dinâmico ao contrato final de submissão.
- Preservar fallback legado quando não houver wizard configurado para a categoria.

## Fora de Escopo
- Step 0 de seleção de intenção para empresas multi-categoria.
- `file_upload` e campos complexos de C&I.
- migração de `wizard_answers` para outro JSONB.
- criação de endpoint novo para resolução de wizard.
- refactor completo do `Lead` para validação 100% guiada por schema.
- redesign completo do tracking de analytics.

## Acceptance Criteria
1. [ ] **Contrato de Resolução**:
   - `GET /api/v1/lead_wizards/resolve` continua sendo o único endpoint de leitura do wizard.
   - O resolver usa `category_id` como base e `preferred_company_id` como filtro de disponibilidade.
   - Se a empresa não estiver associada à categoria, a resposta diferencia indisponibilidade de empresa de fallback por ausência de wizard.
   - Se não houver wizard configurado para a categoria, o sistema continua retornando o fallback legado.
2. [ ] **Contrato de Schema**:
   - O schema segue `fields[].key` como chave canônica.
   - A Fase 1 limita os tipos de campo aos já suportados pelo frontend atual: `text`, `email`, `tel`, `select`, `radio`, `checkbox`, `currency`, `zipcode`, `slider`, `textarea`.
   - `template_key`, `template_version` e `thank_you_config` continuam disponíveis no payload de resolução.
3. [ ] **Persistência e Compatibilidade**:
   - `leads.wizard_answers` permanece como source of truth para campos variáveis.
   - `LeadWizard::Creator` continua aceitando payloads legados compatíveis com `snake_case` e `camelCase`, quando aplicável.
   - Os campos obrigatórios atuais do `Lead` continuam sendo persistidos nas colunas reais necessárias ao fluxo OTP.
   - `product_vertical` e `category_id` ficam coerentes com a categoria resolvida.
4. [ ] **Alinhamento Frontend/Backend**:
   - O frontend dinâmico envia payload compatível com o `LeadWizard::Creator`.
   - Campos destinados ao core obrigatório do `Lead` não ficam presos somente em `wizard_answers`.
   - O fallback legado continua renderizável pelo engine atual.
5. [ ] **Compatibilidade Operacional**:
   - O fluxo atual de criação de lead com OTP continua funcional.
   - Não é criado endpoint paralelo para wizard.
   - Não é introduzido novo JSONB como substituto de `wizard_answers` nesta fase.

## Dev Notes
### Decisão de Compatibilidade
Esta story adota explicitamente a **Estratégia A**:

- manter o core obrigatório atual do `Lead`
- mapear campos mínimos do wizard para colunas reais
- adiar a remoção das validações globais do fluxo solar

### Contrato Inicial Recomendado
- `fields[].key` como identificador único de campo
- `lead` contendo os campos de contato e os campos necessários ao core do `Lead`
- `wizard_answers` contendo os campos específicos da vertical
