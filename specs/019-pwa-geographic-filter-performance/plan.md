# PDR | Decisões e plano técnico

## Arquitetura proposta
UI → adaptadores existentes → useGeographyCatalog → QueryClient compartilhado → persistência versionada → API pública de taxonomia → proxy restrito → Rails BrLocations pré-aquecido. SW/HTTP/CDN são camadas de transporte, não fontes concorrentes de verdade. Listagem/contagem/sede/cobertura seguem caminho dinâmico separado (Rails/Redis/PostgreSQL).

ADR-01: adotar TanStack Query existente, sem biblioteca concorrente. QueryClient único no escopo de aplicação, isolado no SSR por request. `staleTime=24h`, `gcTime=7d` como ponto inicial, alinhado com TTL; preservar versões de contrato. Cache válido sincronamente via QueryClient/initialData; persistência por UF, sem Map duplicando todo estado reativo. `initialDataUpdatedAt` deve refletir timestamp real. Uma fonte reativa; storage é backing store.
ADR-02: normalizar UF e usar queryKey `['geo','official-cities', uf, revision]`; versão de schema separada de revisão de conteúdo. Obter versão via metadata/header compatível, revalidar com TTL; em nova revisão invalidar seletivamente sem loop. Cancelamento cooperativo e guard por seleção, não throttle.
ADR-03: preservar API existente e payload; digest canônico + ETag por recurso/UF e representação. Warmup antes de readiness; medir memória e tempo de boot no modo Puma efetivo. Não aquecer DB ou rede externa no initializer.
ADR-04: proxy deny-by-default; cache público somente GET de endpoints exatos, query validada, sem auth/cookie de sessão; caso contrário no-store. Sem Set-Cookie, sem cache de erros; preserve Vary, validators e status 304 sem body. Não alterar regras globais do proxy. Edge key inclui UF, query permitida e variantes necessárias. Evitar cache poisoning.
ADR-05: /count independente do catálogo, com chave baseada em todos filtros que influenciam resultado. Se route não existir, corrigir rota/controller conforme contrato existente; sem retries 404. Fallback por metadado de paginação se comprovadamente equivalente; caso contrário estado neutro sem bloquear apply.
ADR-06: somente empresas elegíveis/ativas no endpoint de presença; validar contrato legado e consumidores antes de alterar. Cache Redis curto (proposta 10 min) com invalidação pós-commit das mudanças relevantes e fallback seguro. Não cachear facetas de cobertura como taxonomia oficial.
ADR-07: PostgreSQL: testar dados representativos, queries e planos antes de escolher índice. Preferir dados normalizados e índice compatível com predicado; função immutable_unaccent só se propriedade e dicionário controlados, com plano de reindex; avaliar trigram apenas se seletividade justifica. Migração concorrente, reversível, limites de lock/statement e recuperação de índices inválidos. Não executar ANALYZE de queries pesadas em produção sem autorização.
ADR-08: SW opcional dedicado a taxonomia, cache por revisão, validação de resposta 200 JSON e sem credentials; teste de upgrade/rollback. Não habilitar flag global offline para todos os endpoints sem auditoria.

## DDD pragmático
Contexto GeographyCatalog (UF, Município oficial, revisão, repositório do catálogo); CompanyDiscovery (presença de empresas, sede, cobertura declarada, critérios, contagem). Objetos de valor: UF validada, município com identidade estável e UF, FilterCriteria normalizado. Não misturar taxonomia com disponibilidade. Use cases: ListOfficialStates, ListOfficialCities, ResolveCompanyLocations, CountCompanies, SearchCompanies. Adaptadores Rails/HTTP/React existentes, sem impor nova estrutura global. GPS/LocationContext é preferência/entrada do usuário, não domínio de cobertura nem fonte oficial.

## UX e geometria
- Barra mobile: 4 colunas, h-11/44 px, labels existentes, sem novos chips nem largura extra. Drawer 70vw, cabeçalho e rodapé fixos, scroll interno, backdrop ≥30% de opacidade se contrato visual confirmar; selects nativos existentes. Preservar tokens, fontes, peso, cor, bordas, espaçamento e ícones atuais; snapshots antes/depois.
- Cache hit: troca sem spinner ou flash. Miss: limpar opções da UF antiga e mostrar estado de loading imediatamente dentro da área existente. City select indisponível durante miss, acessível com status; erro com retry e sem deslocar layout crítico. Não colocar botão dentro de select nativo.
- Desktop: busca textual local na seção atual, sem mudar dimensões externas; virtualização ou janela progressiva com foco, busca completa, multi-UF e seleção persistente. Evitar elemento interativo inacessível fora da janela.
- Preservar animação existente (auditoria indica 240ms); respeitar prefers-reduced-motion e não animar troca de dados nem bloquear main thread. Sem redesenhar o filtro.
- Journey: abrir → UF atual prefetched → selecionar → opções corretas → cidade → contagem opcional → aplicar → resultados coerentes; fechar/cancelar mantém estado aplicado conforme contrato; retry e offline explícitos.

## Fases / esforço
Auditoria estimou F0–F5 = 24 SP (3+5+3+5+3+5). Acrescentar F-1 de ambiente/isolamento (3 SP) e F6 de release/aceite (5 SP): total proposto 32 SP, estimativa de backlog, não prazo. F1 e F2 paralelizáveis após F0 com coordenação de contratos; F3 depende de F2; F4 de F1; F5 depende de contratos e dados representativos. F6 depende de todos os gates de release.

## Rollout / rollback
Branch isolada `feat/019-pwa-geographic-filter-performance` a partir da base aprovada; não sobrescrever Spec 018 nem alterações locais. Commits pequenos por fase, PR(s) rastreados. Flags propostas: `NEXT_PUBLIC_ENABLE_UNIFIED_GEO_CACHE`, server-side `ENABLE_GEO_PUBLIC_CACHE`, e flag específica de geo SW se arquitetura permitir; validar naming e mecanismo de build/deploy. NEXT_PUBLIC é build-time: rollback exige rebuild ou mecanismo runtime já existente. Flags desligadas não devem reintroduzir bug de correção P0: mantenha correção mínima segura.
Staging → smoke → canário quando suportado → expansão após gates; se não houver canário, rollout controlado com imagem anterior identificada, smoke imediato e rollback via fluxo existente. Produção só mediante autorização/política do repo. Invalidar somente cache geo, restaurar proxy no-store, reverter imagem e migrations de forma independente; não remover índices que ainda sustentem versão em execução. Preservar secrets e não desativar proteções. Reverter se dados de UF incorretos, vazamento, erro funcional, 5xx ou OOM atribuíveis, ou p95 > orçamento sustentado conforme amostra.
